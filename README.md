# LexSync — Indian Labour Law, Structured

LexSync is a personal HR-tech project by Athul Saji (MSW-HRDM, Christ University Bengaluru):
a structured **learning and reference app for Indian labour law** — zero budget, no build tools,
no frameworks, no backend.

It covers the 4 Labour Codes plus the major pre-code Acts (18 acts in the corpus and growing),
with per-section study notes, HR-activity browsing, payroll calculators, quizzes, an
applicability engine ("which laws apply to my establishment?"), compliance checklists,
cross-references between old Acts and new Codes, and a local-first AI assistant.

**Status honesty:** section notes are AI-drafted study summaries until verified against official
sources. The UI badges every provision: 🟢 *Verified against official source* vs
🟡 *AI study notes — unverified*. Nothing here is legal advice — see the footer disclaimer.

## Run it

**Easiest (offline):** open `dist/lexsync.html` in any browser — double-click works, no server needed.

**Dev mode** (multi-file source):
```bash
cd ~/workspace/lexsync
python3 -m http.server 8000
# open http://localhost:8000
```
Dev mode fetches `data/*.json` over http (browsers block `fetch` on `file://`).

## Build

```bash
python3 tools/build.py
```

This globs `data/acts/*.json` **dynamically** (never hardcoded), inlines `css/` + `js/` +
the whole JSON corpus into a single `dist/lexsync.html`, validates that every checklist and
cross-reference points at a real provision, and refreshes `data/index.json` (used by dev mode).
**Run the build as the last step after any data change** so `dist/` picks up new/removed acts.

`dist/` **is committed** to the repo on purpose: the app is a single self-contained file, so it
can be hosted as-is (e.g. GitHub Pages) with zero deployment steps.

## Update the data

```bash
python3 tools/update.py            # re-runs verification, bumps data/version.json
python3 tools/verify.py --help     # verification pipeline (official-source metadata)
python3 tools/build.py             # rebuild dist/ afterwards — always the final step
```

In the app, the footer **“🔄 Check for updates”** button compares the bundled `data_version`
with the manifest published in the project repo (`data/version.json → manifest_url`) and tells
the user when newer data is available. It changes nothing by itself.

## Project layout

```
index.html            app shell (nav, view containers, footer disclaimer)
css/styles.css        look & feel carried over from LexSync Lite
css/views.css         styles for the new views (applicability, checklists, xrefs…)
js/                   one module per view (plain scripts, no bundler)
  app.js              router/shell, state, deep links, boot
  data.js             corpus loading (embedded in dist, fetch in dev) + badge model
  lawBrowser.js       browse by law: categories, tabs, chapters, search, section cards
  activityBrowser.js  browse by HR activity
  calculators.js      PF, ESI, gratuity, bonus estimators
  assistant.js        local-first grounded Q&A (+ optional Claude API key, warned)
  games.js            6 quiz modes generated from the corpus
  applicability.js    "which laws apply?" engine with threshold logic + counsel disclaimer
  checklists.js       compliance checklists with deep links into the law browser
  xrefs.js            curated cross-references ("Related provisions")
  updateCheck.js      "check for updates" against the repo manifest
data/
  acts/*.json         one file per act/code: chapters + provisions (schema in docs/ARCHITECTURE.md)
  checklists.json     checklist definitions (act slug + section number per item)
  xrefs.json          curated cross-act topic links
  version.json        {data_version, released_at, changelog[], manifest_url}
  index.json          regenerated by build.py (dev-mode act list)
  provenance/         official-source metadata from the verification pipeline
tools/
  build.py            bundle everything into dist/lexsync.html
  update.py           bump data version after verification runs
  verify.py           official-source verification pipeline
dist/lexsync.html     the built, offline-capable single file (committed)
docs/ARCHITECTURE.md  data flow, module map, verification model, build pipeline
```

See `docs/ARCHITECTURE.md` for the full technical picture.
